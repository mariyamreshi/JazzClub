# ขอบเขตจาก proposal และเรื่องที่ต้องตกลง

## ขอบเขตที่ระบุแล้ว

- ฐานข้อมูลอย่างน้อย 8 entities ใน 3NF และอย่างน้อย 2 ความสัมพันธ์ M:N ที่มี bridge table
- CRUD สำหรับข้อมูลหลัก รวม frontend, backend และ MySQL
- Bridge tables ใน proposal คือ Order_Item และ Show_Attendance; Employee_Shift ใช้เชื่อมพนักงานกับการแสดงด้วย
- ใช้ข้อมูลจำลอง รวมกรณียกเลิก ไม่มาใช้บริการ และความต้องการสูง/ต่ำ
- ไม่มี login, roles และแอปมือถือ
- มีการบันทึก Payment ตาม proposal; ยังไม่มีข้อกำหนดให้เชื่อม payment gateway

## รายงานที่ต้องมี

1. โต๊ะใดว่างในวันและเวลาที่เลือก
2. แต่ละการแสดงมี stock และพนักงานเพียงพอหรือไม่
3. การจองแต่ละรายการมีออเดอร์และการชำระเงินอะไรบ้าง

## ต้องตอบก่อนออกแบบ schema และ logic จริง

| เรื่อง | คำถาม/ช่องว่างจาก proposal | ผลต่อระบบ |
| --- | --- | --- |
| ช่วงเวลาการจอง | จองตามรอบการแสดง หรือระบุเวลาเริ่มและสิ้นสุดเอง? | Reservation มีเพียง DateTime ยังตรวจช่วงเวลาทับซ้อนไม่ครบ |
| จำนวนโต๊ะ | หนึ่งการจองใช้หนึ่งโต๊ะตาม proposal หรือหลายโต๊ะ? จำนวนผู้มาใช้บริการเก็บที่ใด? | มีผลต่อความสัมพันธ์และการตรวจ capacity |
| การจองกับการแสดง | Reservation ต้องผูกกับ Show โดยตรงหรือจับคู่จากช่วงเวลา? Show_Attendance ใช้บันทึกผู้จองหรือผู้เข้าชมจริง? | ทำให้การนับความต้องการต่อ show และ attendance ไม่คลาดเคลื่อน |
| Stock | นับจำนวนเมนูพร้อมขายตาม Menu_Item หรือรวมวัตถุดิบ/สูตรอาหาร? ตัดและคืน stock เมื่อใด? | ถ้าใช้วัตถุดิบต้องเพิ่ม entities และขอบเขตงาน |
| Stock เพียงพอ | เปรียบเทียบกับยอดคาดการณ์ต่อ show หรือจำนวนขั้นต่ำที่กำหนด? | StockQuantity อย่างเดียวยังตอบรายงานความพร้อมไม่ได้ |
| พนักงานเพียงพอ | ต้องการกี่คนต่อ show และต้องแยกตำแหน่งหรือไม่? | ต้องมีเกณฑ์ความต้องการและตรวจเวรซ้อน |
| Payment | ใช้หนึ่ง order ต่อหนึ่ง payment ตาม proposal ใช่หรือไม่? order ที่ยังไม่จ่ายต้องมีสถานะอย่างไร? | ควรรองรับก่อนชำระเงินโดยยังไม่มี payment; ผ่อน/แยกจ่ายจะเปลี่ยน cardinality |
| ยอดออเดอร์ | TotalAmount คำนวณจาก Order_Item หรือเก็บ snapshot พร้อมวิธีรักษาความสอดคล้อง? | ป้องกันยอดไม่ตรงหลังแก้รายการ และใช้ PriceAtTime รักษาราคาตอนสั่ง |
| ลบข้อมูล | รายการที่มีประวัติการจอง/ชำระเงินจะลบ ยกเลิก หรือปิดใช้งาน? | ต้องตกลง foreign keys และพฤติกรรม CRUD |

เรื่องเหล่านี้ไม่ขัดกับการเตรียมโฟลเดอร์ แต่ยังไม่ควรสร้าง schema ที่ล็อกคำตอบโดยไม่มีข้อสรุป

## ตรวจ ERD รอบถัดไป

- เติม Payment และเส้นเชื่อมที่ยังไม่ครบในภาพ เช่น Table → Order และ Customer → Show_Attendance โดย Payment อ้าง Order ผ่าน `order_id`
- เติม keys/attributes ของ Order_Item และ Show_Attendance ให้ครบตามความหมายที่ตกลง
- ทบทวน cardinality ของ Employee_Shift ให้สอดคล้องกับตารางความสัมพันธ์
- ตรวจ 3NF, foreign keys, uniqueness, status และกติกาเวลา แล้วบันทึก data dictionary ใน `docs/erd/`
- ทดสอบความพยายามจองซ้อนผ่าน API ภายหลัง; seed ที่ import สำเร็จไม่ควรใส่แถวที่ละเมิด constraints โดยตั้งใจ
